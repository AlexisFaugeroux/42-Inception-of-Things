Kubernetes architecture

A cluster is split in two. The control plane decides what should run and where. The worker nodes actually run your containers, grouped in pods. Every component talks to the others only through the API server.

Control plane Worker node & node agents Pods & containers Networking objects (Service, Ingress)

What each piece does

Control plane

kube-apiserver

The only entry point. Validates and stores every object (Deployments, Pods…). kubectl, the other components and the kubelets all talk to it over HTTPS.

etcd

Distributed key-value database holding the whole cluster state. Only the API server reads and writes it. If you lose it without a backup, you lose the cluster.

kube-scheduler

Watches for pods with no node yet and picks one, based on CPU/RAM requests, affinities, taints and tolerations.

kube-controller-manager

Runs the reconcile loops: keep N replicas of a Deployment, notice dead nodes, create ServiceAccounts… It compares desired and actual state and fixes the gap.

cloud-controller-manager

Only on cloud providers. Creates real load balancers for type: LoadBalancer Services, attaches disks, and so on.

On every worker node

kubelet

The node agent. Watches the API server for pods assigned to its node, asks the runtime to start them, runs health probes and reports status.

kube-proxy

Programs iptables/IPVS rules so traffic sent to a Service IP reaches one of its pods. Some CNIs (Cilium, GKE Dataplane V2) replace it.

Container runtime

Pulls images and runs containers. Usually containerd, accessed by the kubelet through the CRI interface.

CNI plugin

Gives each pod its own IP and lets pods on different nodes reach each other directly. Examples: Flannel, Calico, Cilium.

Workloads & networking

Pod

The smallest unit Kubernetes schedules: one or more containers that share an IP, a network namespace and volumes. Pods are disposable and get a new IP when recreated.

Service

A stable virtual IP and DNS name (web.default.svc) in front of a changing set of pods, selected by labels.

Ingress

HTTP routing rules (host, path → Service). An Ingress controller such as Traefik reads them and actually routes the traffic.

What happens on kubectl apply -f deployment.yaml

  1. kubectl → API server. The manifest is sent over HTTPS, authenticated, validated, then stored in etcd as the desired state.
  2. Controller manager reacts. The Deployment controller sees the new Deployment and creates a ReplicaSet, which creates 3 Pod objects. They're Pending, with no node yet.
  3. Scheduler assigns nodes. For each pending pod it filters and scores the nodes, then writes the chosen node name into the pod through the API server.
  4. kubelet starts containers. The kubelet on that node sees a pod assigned to it, asks containerd to pull the image and start the containers, and the CNI gives the pod an IP.
  5. Status flows back. The kubelet reports Running and probe results. The pod's IP is added to the Service's endpoints and kube-proxy updates its rules, so traffic starts flowing.
  6. Reconciliation never stops. If a pod or a node dies, the controllers see fewer replicas than desired and the cycle starts again from step 2.
